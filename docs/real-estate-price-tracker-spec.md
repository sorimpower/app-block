# 부동산 호가·실거래가 추적 기능 명세

> 작성 기준일: 2026-09-28  
> 상태: 제품 명세 초안. 네이버 부동산 호가 자동 수집은 공식 사용 허가 또는 정식 데이터 계약 확인 전까지 구현 확정이 아니다.

## 1. 한 문장 정의

관심 아파트와 평형을 등록하면 현재 매물의 호가 변화, 사라진 매물, 국토교통부 실거래가를 시간순으로 함께 보여주고 최대 5개 아파트의 가격 변화를 같은 기준으로 비교하는 개인용 추적 기능이다.

## 2. 제품 목표

- 사용자가 매일 네이버 부동산을 반복해서 열지 않아도 관심 단지·평형의 호가 흐름을 확인한다.
- 현재 최저가만 보여주는 것이 아니라 개별 매물의 등장, 가격 변경, 노출 종료 이력을 보존한다.
- 호가와 실거래가를 같은 그래프에서 구분해 가격 기대와 실제 체결 사이의 차이를 파악한다.
- 서로 가격대가 다른 아파트도 원화, ㎡당 가격, 기준일 대비 변동률로 공정하게 비교한다.
- 데이터가 없거나 수집이 실패한 상태를 가격 변화로 오인하지 않게 한다.

## 3. 핵심 제품 원칙

1. `사라진 매물`을 `거래 완료`라고 단정하지 않는다. 화면에는 `네이버 노출 종료` 또는 `매물 사라짐`으로 표시한다.
2. 호가, 실거래가, 앱이 계산한 통계를 색상과 범례로 명확히 구분한다.
3. 평형의 기준 식별자는 평(예: 34평)이 아니라 `전용면적 ㎡ + 단지 식별자`다. 평 표기는 사용자 편의를 위한 보조 정보다.
4. 동기화 실패, 목록 일부 누락, 제공자 응답 변경은 매물 삭제로 처리하지 않는다.
5. 네이버 내부 비공개 API나 웹 화면 자동 수집은 공식 허용 여부를 확인한 뒤에만 운영한다. CAPTCHA 우회, 로그인 자동화, IP 회전 등 기술적 제한 우회는 하지 않는다.
6. 과거 스냅샷을 수정하지 않는다. 정정은 새 상태와 이벤트로 누적해 당시 화면을 재현할 수 있게 한다.

## 4. 데이터 소스 결정

### 4.1 실거래가 — 확정

주 데이터 소스는 공공데이터포털의 `국토교통부_아파트 매매 실거래가 자료`다.

- 법정동 코드 앞 5자리와 계약년월로 조회한다.
- 거래금액, 계약일, 전용면적, 층, 건축연도, 거래유형 등 응답 필드를 원본과 함께 저장한다.
- API가 해제일 또는 취소 상태를 제공하면 원 거래를 삭제하지 않고 `CANCELLED`로 표시한다.
- 월 단위 조회 결과는 서버에서 캐시하고, 최근 3개월은 정정·해제 반영을 위해 주기적으로 다시 확인한다.
- 프로젝트의 기존 Firebase Callable Function `lookupMolitApartmentTrades`와 `MolitRealEstateProvider`를 공통 실거래 저장소가 사용하는 Provider로 확장한다.
- 필요 시 전월세는 별도 공개 API로 후속 추가한다. 매매 MVP에는 포함하지 않는다.

공식 자료:

- [국토교통부 아파트 매매 실거래가 자료](https://www.data.go.kr/data/15126469/openapi.do)
- [국토교통부 아파트 전월세 실거래가 자료](https://www.data.go.kr/data/15126474/openapi.do)
- [국토교통부 공동주택 단지 목록제공 서비스](https://www.data.go.kr/data/15057332/openapi.do)
- [국토교통부 공동주택 기본 정보제공 서비스](https://www.data.go.kr/data/15058453/openapi.do)

### 4.2 단지 검색·식별 — 확정

- K-apt 공동주택 단지 목록과 기본 정보 API를 검색 후보의 기준 데이터로 사용한다.
- 사용자가 단지를 선택할 때 단지명, 도로명/지번 주소, 법정동 코드, K-apt 단지 코드, 좌표를 저장한다.
- 실거래가의 단지명·지번과 K-apt 단지가 자동 매칭되지 않으면 후보를 보여주고 사용자가 한 번 확인한다.
- 네이버 단지 식별자가 확보되면 별도 필드로 매핑하며 K-apt/국토부 식별자를 대체하지 않는다.
- 평형은 전용면적을 기준으로 사용자가 선택한다. 같은 전용면적에 공급면적 타입이 여럿이면 타입명을 함께 저장한다.

### 4.3 네이버 부동산 호가 — 조건부 핵심

2026-09-28 기준 공식 NAVER API HUB 공개 목록에는 검색과 Data Lab API만 안내되어 있고 부동산 매물 API는 확인되지 않는다. 네이버 서비스 이용약관은 사전 허락 없는 자동화 수단을 이용한 수집 등 사람의 실제 이용을 전제로 한 서비스의 비정상적 이용을 금지한다. 따라서 웹·앱이 쓰는 비공개 엔드포인트를 곧바로 운영 API로 채택하지 않는다.

호가 Provider 우선순위:

1. 네이버 또는 네이버 부동산 데이터 제공 주체와의 공식 제휴·사용 승인
2. 저장·재노출·이력 보존을 허용하는 정식 부동산 매물 데이터 공급 계약
3. 위 경로가 불가능하면 사용자가 네이버 매물 링크를 공유해 수동 스냅샷을 만드는 제한 모드

자동 수집은 다음이 서면 또는 명시적 약관으로 확인된 경우에만 활성화한다.

- 호출 가능한 공식 엔드포인트와 인증 방식
- 허용 호출량과 동기화 주기
- 매물 원문, 가격, 중개사 정보의 저장 가능 범위와 보존 기간
- 앱 내 재노출과 파생 통계 생성 가능 여부
- 매물 ID의 안정성과 삭제·종료 상태 제공 방식

공식 확인 자료:

- [NAVER API HUB 제공 API](https://guide.ncloud-docs.com/docs/apihub-overview)
- [네이버 서비스 이용약관](https://policy.naver.com/rules/service.html)
- [NAVER API 서비스 이용약관](https://developers.naver.com/products/terms/)

## 5. 정보 구조

기능명은 `부동산 추적`으로 한다. 기본 탭은 다음 세 개다.

1. `관심`: 등록한 단지·평형의 현재 호가와 최근 변화
2. `비교`: 최대 5개 단지·평형의 가격 변화 비교
3. `변화`: 가격 인하, 신규, 사라짐, 재등장, 새 실거래의 통합 타임라인

상세 화면은 탭이 아니라 관심 항목을 눌러 진입한다.

## 6. 주요 사용자 흐름

### 6.1 관심 항목 등록

1. `관심 추가`를 누른다.
2. 단지명 또는 주소를 검색한다.
3. 주소와 세대수 등으로 정확한 단지를 확인한다.
4. 전용면적과 보조 평형명을 선택한다.
5. 매매를 기본 거래 유형으로 선택한다.
6. 알림 조건을 선택한다.
7. 네이버 단지·평형 자동 매핑 결과를 확인하고 저장한다.

필수 입력은 단지와 전용면적뿐이다. 동, 층, 방향, 가격 범위는 선택 필터다.

### 6.2 관심 목록

각 카드에 다음을 표시한다.

- 단지명, 전용면적, 보조 평형명
- 현재 활성 매물 수와 중복 추정 제외 매물 수
- 현재 최저 호가, 중앙 호가, 25~75% 호가 범위
- 최근 실거래가와 거래일
- 7일·30일 호가 중앙값 변화
- 호가 중앙값과 최근 3개월 실거래 중앙값의 차이
- 마지막 정상 동기화 시각과 데이터 출처
- 오늘의 신규·가격 인하·사라짐 건수

### 6.3 상세 화면

#### 상단 요약

- `현재 호가`: 최저/중앙/최고, 활성 매물 수
- `최근 실거래`: 가격, 계약일, 층
- `호가-실거래 차이`: 금액과 비율
- `시장 움직임`: 최근 30일 신규·인하·사라짐 수

#### 가격 그래프

- 기간: `1개월 / 3개월 / 6개월 / 1년 / 전체`
- 호가: 일별 최저가 선, 중앙값 선, 25~75% 범위 밴드
- 실거래: 계약일 기준 점으로 표시하고 점을 임의의 연속선으로 보간하지 않는다.
- 보조축 또는 하단 막대: 활성 매물 수
- 필터: 전체/저층/중층/고층, 동, 방향, 타입. 정보가 없는 필드는 `미상`으로 유지한다.
- 그래프 지점을 누르면 당시 활성 매물 수, 가격 범위, 신규·인하·사라짐 수와 실거래 상세를 보여준다.
- 동기화 실패일은 선을 이어 실제 가격처럼 보이지 않게 빈 구간으로 표시한다.

#### 매물 목록

- `현재 매물`과 `사라진 매물`을 구분한다.
- 현재 매물은 가격순, 가격 인하순, 등록일순, 마지막 확인순으로 정렬한다.
- 매물 카드: 호가, 전용/공급면적, 층 구간, 방향, 동, 특징, 중개사, 최초 발견일, 마지막 확인일, 가격 변경 횟수, 원문 링크.
- 여러 중개사가 같은 물건을 올린 것으로 추정되면 `중복 후보 N개`로 묶되 원본을 펼쳐볼 수 있게 한다.
- 사라진 매물은 마지막 호가에 취소선을 긋지 않고 상태 배지 `노출 종료`와 마지막 확인일을 표시한다. 실제 매매 완료로 표현하지 않는다.
- 다시 발견되면 같은 매물로 식별 가능한 경우 `재등장` 이벤트를 만들고 이전 이력과 연결한다.

#### 실거래 목록

- 계약일, 거래금액, 전용면적, 층, 거래유형, 해제 여부를 표시한다.
- 취소된 거래는 숨기지 않고 `해제` 배지와 함께 남긴다.
- 동일 전용면적의 허용 오차는 기본 ±0.5㎡이며 사용자가 전체 타입을 선택한 경우에만 범위를 넓힌다.

### 6.4 변화 타임라인

이벤트 유형:

- 신규 매물
- 호가 인상/인하
- 노출 종료 후보
- 노출 종료 확정
- 재등장
- 새 실거래
- 실거래 해제
- 수집 실패/복구

날짜, 단지, 평형, 이벤트 유형으로 필터링한다. 하루 동안 같은 매물에서 여러 번 가격이 바뀌면 최종 가격만 덮어쓰지 않고 변경 순서를 보존한다.

## 7. 매물 상태 판정

상태는 다음 상태 기계로 관리한다.

```text
ACTIVE
  ├─ 정상 전체 수집에서 1회 미발견 → MISSING_PENDING
  └─ 제공자가 종료 상태 명시 → REMOVED

MISSING_PENDING
  ├─ 다음 정상 수집에서 발견 → ACTIVE
  └─ 연속 2회 이상 미발견 → REMOVED

REMOVED
  └─ 안정 식별자가 같거나 재등장 기준 충족 → RELISTED → ACTIVE
```

- 수집 요청 실패, 페이지 일부 실패, 응답 건수 급감, 파서 스키마 오류가 있으면 해당 실행은 삭제 판정에 사용하지 않는다.
- 기본 자동 수집 간격을 6시간으로 가정하면 연속 2회 미발견 후 약 12시간 내 종료 확정이 가능하다. Provider 계약 조건에 따라 간격은 조정한다.
- `REMOVED`는 로컬·서버 이력에서 삭제하지 않는다.
- 안정적인 제공자 매물 ID가 없을 때는 단지, 전용면적, 가격, 동/층 구간, 방향, 중개사 확인번호 등의 지문으로 재등장을 추정하고 `추정 연결`임을 내부에 기록한다.

## 8. 비교 기능

### 8.1 비교 대상

- 최소 2개, 최대 5개의 `단지 + 전용면적` 조합을 선택한다.
- 같은 단지를 다른 평형으로 중복 선택할 수 있다.
- 색상은 최대 5개까지 고정 배정하고 모든 그래프와 범례에서 유지한다.

### 8.2 비교 지표

- 현재 최저 호가
- 현재 중앙 호가
- 최근 3개월 실거래 중앙값
- ㎡당 호가 및 실거래가
- 1개월·3개월·6개월 호가 변동률
- 기준일을 100으로 둔 상대 가격 지수
- 활성 매물 수 변화
- 가격 인하 매물 비율
- 호가-실거래 차이
- 마지막 실거래 이후 경과일

### 8.3 비교 그래프 규칙

- `절대 가격 / ㎡당 가격 / 기준일 대비 %`를 전환한다.
- 호가와 실거래를 동시에 보거나 한쪽만 선택할 수 있다.
- 비교 시작일에 데이터가 없는 항목은 첫 정상 데이터일부터 그리며 임의로 과거 값을 채우지 않는다.
- 거래가 드문 단지의 실거래를 선으로 연결해 연속 시세처럼 보이게 하지 않는다.
- 데이터 수집 기간이 다른 경우 각 항목의 시작일과 수집 완성도를 표시한다.

## 9. 알림

관심 항목별로 다음 알림을 켜고 끌 수 있다.

- 새 최저가 등장
- 개별 매물 가격 인하/인상
- 지정 금액 이하 매물 등장
- 매물 노출 종료 확정
- 새 실거래 등록 및 실거래 해제
- 호가 중앙값이 7일 기준 지정 비율 이상 변동

같은 동기화 실행에서 발생한 이벤트는 단지·평형별로 묶어 한 번만 알린다. 수집 장애와 정상적인 `변화 없음`을 구분하며 장애 중에는 가격 알림을 보내지 않는다.

## 10. 통계 계산 규칙

- 일별 호가 통계는 해당 시점의 `ACTIVE` 매물만 사용한다.
- 대표값은 평균보다 이상치에 덜 민감한 중앙값을 기본으로 한다.
- 최저가는 전체 매물 최저와 중복 후보를 묶은 뒤의 추정 최저를 함께 검증한다.
- 중복 매물은 제공자가 동일 물건 식별자를 주면 확정 그룹으로 묶고, 그렇지 않으면 휴리스틱 결과를 `중복 추정`으로 표시한다.
- 가격 변동률은 `(현재값 - 기준값) / 기준값 × 100`으로 계산한다.
- 호가-실거래 차이의 실거래 기준은 기본 최근 3개월 동일 평형 중앙값이다. 거래가 없으면 6개월, 12개월 순으로 확장하고 적용 기간을 표시한다.
- 실거래 금액은 계약일 기준이며 신고·수집일을 가격 시점으로 사용하지 않는다.

## 12. 시스템 구조

```text
국토부/K-apt 공식 API ─┐
                       ├─ Firebase 수집 함수 ─ 원본/정규화 저장소 ─ 집계 작업
승인된 호가 Provider ──┘                                  │
                                                          ├─ 변화 이벤트/FCM
Android 앱 ─ Callable/HTTPS API ─ 권한 확인 ───────────────┘
           └─ Room 오프라인 캐시 ─ Compose 그래프/목록/비교
```

- 앱이 네이버 비공개 엔드포인트를 직접 호출하지 않는다.
- 공공데이터 서비스 키와 Provider 자격증명은 Firebase Secret Manager에 둔다.
- 호가 수집은 Cloud Scheduler 기반으로 실행하되 Provider 허용량과 약관을 우선한다.
- 관심 항목이 없는 단지·평형은 자동 수집하지 않는다.
- 서버 수집 함수는 Provider 인터페이스로 분리해 네이버 승인형, 계약형, 수동형을 교체할 수 있게 한다.
- 같은 지역·월 실거래 요청은 공유 캐시해 공공 API 호출량을 줄인다.
- 화면은 마지막 성공 데이터와 `마지막 업데이트`를 보여주며 수집 실패 시 이전 값이 최신인 것처럼 표시하지 않는다.

## 14. 예외·오류 상태

- 네이버 단지 매핑 실패: 후보 선택 또는 링크 붙여넣기 요청
- 해당 평형 매물 없음: `현재 확인된 매물 없음`과 마지막 매물 종료일 표시
- 실거래 없음: 조회 기간을 확장하되 별도 표시
- Provider 인증 만료/차단: 기존 데이터는 읽기 전용으로 유지하고 동기화 중단 사유 표시
- 응답 구조 변경: 해당 실행 전체를 실패 처리하고 삭제 이벤트 생성 금지
- 일부 페이지만 실패: 데이터 품질 `PARTIAL`, 삭제 판정과 집계 확정 금지
- 단지명 변경/재건축: 별칭과 단지 버전을 보존하고 자동 병합하지 않음
- 앱 재설치/기기 오프라인: 서버 관심 목록과 이력을 다시 동기화

## 15. 개인정보·법적·운영 안전

- 주소와 관심 목록은 개인의 자산 관심을 드러낼 수 있으므로 로그, Analytics, Crashlytics에 원문을 남기지 않는다.
- 중개사 전화번호와 개인 식별 정보는 기능상 반드시 필요한 범위를 넘겨 저장하지 않는다.
- 원문 링크와 출처를 표시하고 데이터 제공자의 표시·캐시·보존 조건을 따른다.
- 네이버 허가가 확인되지 않으면 자동 호가 수집 플래그를 서버에서 비활성화한다.
- 약관 위반 가능성이 있는 우회 수집 코드는 앱과 운영 서버에 배포하지 않는다.
- 호가와 실거래는 참고 정보이며 매수·매도 권유나 감정가로 표현하지 않는다.

## 16. MVP와 단계별 구현

### Phase 0 — 데이터 수집 타당성 검증 (필수 Go/No-Go)

- 네이버/NAVER Cloud 문의를 통해 부동산 매물 API 또는 데이터 사용 계약 가능 여부 확인
- 저장, 이력화, 앱 재노출, 파생 통계 허용 범위 확인
- 단지·평형·매물 ID 안정성, 페이지 완전성, 종료 상태, 호출 한도 검증
- 국토부 실거래와 K-apt 단지 매칭 샘플 20개 검증
- 결과 문서화 후 자동 호가 기능 Go/No-Go 결정

종료 조건: 합법적·안정적 자동 수집 경로가 확인되지 않으면 Phase 2 자동 수집은 시작하지 않고 수동 링크 스냅샷 또는 다른 계약형 Provider를 선택한다.

### Phase 1 — 관심 목록 + 실거래 기반

- 단지/평형 검색과 관심 등록
- 국토부 실거래 이력, 취소 거래, 기본 그래프
- 최대 5개 실거래 비교
- 서버·Room 캐시와 동기화 상태

### Phase 2 — 호가 추적 MVP

- 승인된 Provider 수집
- 현재 호가, 일별 스냅샷, 개별 가격 변경
- 신규/사라짐/재등장 상태
- 호가와 실거래 통합 그래프
- 수집 품질 감시와 장애 시 삭제 판정 차단

### Phase 3 — 비교·알림 고도화

- 최대 5개 호가 비교
- ㎡당 가격과 기준일 대비 지수
- 가격 인하, 새 최저가, 매물 종료, 새 실거래 알림
- 중복 매물 그룹과 층/동/방향 필터

### Phase 4 — 인사이트

- 매물 재고 증감과 소진 속도
- 오래된 매물과 반복 재등록 탐지
- 층 구간별 호가·실거래 차이
- 전세가율 및 매매·전세 동시 추적

## 17. 추가 추천 기능

우선순위가 높은 확장 아이디어는 다음과 같다.

1. `호가-실거래 갭`: 현재 매도 기대와 최근 체결 가격 차이를 금액·비율로 표시
2. `매물 재고 온도`: 신규 대비 사라짐, 가격 인하 비율, 활성 매물 증감으로 공급 압력을 관찰
3. `오래된 매물`: 최초 발견 후 30/60/90일이 지난 매물과 누적 인하 횟수 표시
4. `재등장 탐지`: 사라졌다 비슷한 조건으로 다시 나온 매물의 이전 가격과 비교
5. `층별 비교`: 저·중·고층 호가와 실거래 분포를 나눠 같은 평형 내 질적 차이를 완화
6. `내 기준가 메모`: 사용자가 생각하는 적정가와 목표 매수가를 저장하고 도달 시 알림
7. `전세가율`: 전월세 공개 API를 연결해 갭과 변화 추적. 매매 MVP 안정화 후 추가

AI가 시세를 예측하거나 매수 결론을 내리는 기능은 초기 범위에서 제외한다. 먼저 관찰 가능한 원본 변화와 계산 근거를 신뢰할 수 있게 만드는 것이 우선이다.

## 18. 수용 기준

### 관심·상세

- 사용자가 단지와 전용면적을 선택해 1분 이내 관심 항목을 등록할 수 있다.
- 마지막 성공 수집 시각과 출처가 모든 가격 화면에서 확인된다.
- 호가 최저·중앙·분포와 실거래가가 시각적으로 구분된다.
- 매물 가격 변경 이력을 시간순으로 확인할 수 있다.

### 사라진 매물

- 정상 전체 수집이 아닌 실행은 매물 종료 판정에 사용되지 않는다.
- 연속 미발견 기준을 충족한 매물만 `노출 종료`로 바뀐다.
- 노출 종료 매물은 마지막 가격·최초/마지막 확인일과 함께 계속 조회된다.
- 재등장 시 이전 이력과 연결되거나 추정 연결 여부가 기록된다.

### 비교

- 2~5개 단지·평형을 선택할 수 있고 6번째 선택은 명확히 차단된다.
- 절대 가격, ㎡당 가격, 기준일 대비 변동률을 전환할 수 있다.
- 데이터가 없는 기간을 임의 보간하지 않는다.

### 신뢰성

- Provider 응답 스키마가 바뀌면 파서가 조용히 잘못된 가격을 저장하지 않고 동기화를 실패시킨다.
- 동일 수집 응답을 다시 처리해도 중복 스냅샷·이벤트가 생성되지 않는다.
- 실거래 정정·해제 시 과거 원본과 상태 변경이 모두 남는다.
- 자동 수집 권한이 없으면 서버 플래그로 즉시 중단할 수 있다.

## 19. 테스트 계획

- K-apt 단지와 국토부 단지명/지번 매칭 및 사용자 확인 분기
- 동일 단지의 유사 전용면적 타입 분리
- 가격 단위 파싱, 억/만원 표시, ㎡당 가격 계산
- 신규 → 가격 인하 → 미발견 1회 → 복귀 → 종료 → 재등장 상태 전이
- 전체 실패와 일부 페이지 실패에서 종료 이벤트가 생성되지 않는지 확인
- 중복 응답의 멱등 처리
- 거래 해제 데이터의 상태 보존
- 일별 중앙값·사분위·활성 수 집계 Golden Test
- 비교 대상 2개/5개/6개 경계
- 데이터 시작일이 다른 비교 그래프
- 오프라인 캐시, 서버 복구, 마지막 성공 시각
- Provider 비활성화 플래그와 자격증명 만료
- 기존 앱 전체 단위 테스트와 Debug APK 빌드

## 20. 구현 전 결정이 필요한 항목

1. 네이버 부동산 자동 수집의 공식 허용 또는 계약 가능 여부
2. 호가 데이터 서버 보존 기간과 원문 재노출 범위
3. 개인용 단일 사용자로 시작할지 다중 사용자 구조를 처음부터 둘지
4. 기본 수집 주기: 6시간 또는 12시간
5. 초기 지원 지역: 서울만 또는 전국
6. 전월세를 MVP에 포함할지 Phase 4로 둘지

가장 중요한 결정은 1번이다. 이 결과가 나오기 전에도 실거래 관심 목록과 비교 기능은 구현할 수 있지만, 호가 자동 추적의 운영 가능성을 전제로 일정과 완성도를 약속해서는 안 된다.
