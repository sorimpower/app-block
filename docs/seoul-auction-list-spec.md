# 부동산 경매 목록 기능명세서

## 1. 문서 정보

- 기능명: **부동산 경매**
- 목적: 매일 갱신되는 서울 소재 고가 아파트 경매 사건을 소림파워 앱에서 빠르게 확인한다.
- 상태: MVP 구현 완료
- 대상 앱: 개인용 Android 앱 SorimPower
- 데이터 원본: Google Apps Script Web App API
- API URL: `https://script.google.com/macros/s/AKfycbw-ryPQ_7E9lOOtxxO4dl0FxoQYf0B5iivY5i4vA1IbYmuP57NYH1dNvWmlxooPVPT70A/exec`

## 2. 배경과 문제

사용자는 매일 새로 등록되거나 내용이 갱신된 부동산 경매 사건을 경매 사이트에서 반복해서 검색하는 불편을 줄이고 싶다. 별도의 Google Apps Script 작업이 매일 오전 8~9시에 경매 데이터를 Google 스프레드시트에 저장하므로, 앱은 이 데이터를 읽어 다음 조건에 맞는 사건만 간결한 목록으로 제공한다.

고정 조회 조건은 다음과 같다.

- 소재지: 서울특별시
- 감정평가액: 10억 원 이상
- 진행 상태: 진행 중
- 용도: 아파트

이 기능의 핵심은 경매 사이트의 모든 기능을 대체하는 것이 아니라, 관심 범위의 사건을 매일 짧은 시간 안에 훑어보게 하는 것이다.

## 3. 목표

- 앱 진입만으로 고정 조건에 맞는 최신 경매 사건을 확인할 수 있다.
- 매각기일, 가격, 주소, 사건번호 등 판단에 필요한 핵심 정보만 우선 표시한다.
- 마지막 데이터 갱신 시각을 명확히 표시하여 데이터의 신선도를 판단할 수 있다.
- 이전 조회와 비교해 새로 등장한 사건을 `신규`로 구분한다.
- 네트워크 장애가 있어도 마지막으로 성공한 목록을 확인할 수 있다.
- API 또는 원본 데이터에 조건 밖 사건이 섞여도 앱에서 한 번 더 제외한다.

- 내려받은 목록의 건물명을 대상으로 하는 아파트명 실시간 부분 검색

## 5. 사용자 시나리오

### 5.1 기본 조회

1. 사용자가 홈에서 **부동산 경매**를 선택한다.
2. 앱은 로컬에 저장된 최근 목록을 즉시 보여준다.
3. 동시에 API 첫 페이지를 요청한다.
4. 성공하면 목록과 마지막 갱신 시각을 갱신한다.
5. 사용자는 매각기일이 가까운 사건부터 핵심 정보를 확인한다.
6. 목록 하단에 도달하면 다음 페이지를 불러온다.

### 5.2 신규 사건 확인

1. 앱이 한 번 이상 성공적으로 동기화되어 기준 목록을 보유한다.
2. 다음 동기화에서 이전에 없던 `itemKey`가 발견된다.
3. 해당 카드에 `신규` 배지를 표시한다.
4. 최초 설치 후 첫 동기화에서는 모든 항목을 신규로 표시하지 않는다.

### 5.3 새로고침 실패

1. 사용자가 화면을 열거나 직접 새로고침한다.
2. 네트워크 또는 API 오류가 발생한다.
3. 저장된 목록이 있으면 그대로 유지하고 상단에 `최신 정보를 불러오지 못했어요`를 표시한다.
4. 저장된 목록이 없으면 오류 안내와 `다시 시도` 버튼을 표시한다.

## 6. 화면 명세

### 6.1 홈 기능 카드

- 제목: `부동산 경매`
- 설명: `서울·감정가 10억 이상 진행 중 아파트`
- 배지: `DAILY`
- 선택 시 경매 목록 화면으로 이동
- 홈의 기능 개수 문구를 실제 카드 수와 일치시킨다.

### 6.2 목록 화면 상단

- 화면 제목: `부동산 경매`
- 공통 보라·핑크 요약 카드: 진행 중 전체 건수와 고정 관심 조건 표시
- 고정 조건은 상단 요약 카드의 `서울 · 아파트 · 감정가 10억 이상` 문구로 간결하게 표시하며 검색·정렬 카드에서 중복 표시하지 않는다.
- 결과 수: `총 N건`
- 데이터 시각: `데이터 갱신 8월 6일 08:42`
- 앱 요청 성공 시각과 원본 데이터 갱신 시각을 혼동하지 않도록 원본의 `lastUpdatedAt`을 사용한다.
- `lastUpdatedAt`이 없으면 `갱신 시각 확인 불가`로 표시한다.

### 6.3 사건 카드

카드에는 API의 모든 필드를 노출하지 않고 아래 정보만 표시한다.

#### 항상 표시

- `신규` 배지: 이전 성공 동기화에 없던 사건만 표시
- 매각기일 및 정규화한 시간: 예) `8월 21일(금) 10:00`. 우상단 버튼과 겹치지 않도록 최대 2줄로 전체 표시
- 남은 기간: 예) `D-15`, 당일이면 `오늘`, 지난 날짜이면 `기일 경과`
- 건물명: 값이 없으면 `아파트 경매`
- 주소: 서울 구·동과 나머지 주소
- 사건번호와 물건번호
- 감정가
- 최저가
- 최저가 비율
- 유찰 횟수
- 담당 법원

#### 조건부 표시

- 비고: 값이 있을 때만 최대 2줄
- 구성물건수: 2개 이상일 때만 `구성물건 N개`
- 경매 장소: 공간이 허용되고 값이 있을 때만 보조 정보로 표시

#### 기본적으로 표시하지 않음

- 법원코드
- 내부사건번호
- 담당계 전화번호
- 관심물건등록수
- 수집일시
- 시도·시군구·동의 개별 원본 필드

전화번호 등 숨긴 필드는 향후 상세 화면이 필요할 때 사용할 수 있도록 데이터 모델에는 유지할 수 있다.

### 6.4 가격 표시

- 원 단위 원본값은 `Long`으로 처리한다.
- 1억 원 이상은 억 단위로 읽기 쉽게 표시한다.
- 예: `1,250,000,000` → `12억 5,000만 원`
- 카드 가격 영역 예시:
  - `감정가 12억 5,000만 원`
  - `최저가 10억 원 · 80%`
- 값이 0이거나 파싱할 수 없으면 `가격 정보 없음`으로 표시하고, 감정가 조건 검증에는 실패한 것으로 처리한다.

### 6.5 목록 상태

#### 최초 로딩

- 카드 형태의 스켈레톤 또는 중앙 로딩 표시
- 기존 캐시가 있으면 로딩 표시 대신 캐시를 즉시 노출

#### 빈 목록

- 문구: `현재 조건에 맞는 진행 중 경매가 없어요.`
- 마지막 갱신 시각은 계속 표시
- `다시 확인` 버튼 제공

#### 전체 요청 실패

- 문구: `경매 목록을 불러오지 못했어요.`
- 원인별 상세 기술 문구는 로그에 남기고 사용자에게는 간단히 표시
- `다시 시도` 버튼 제공

#### 다음 페이지 실패

- 현재 목록은 유지
- 하단에 `다음 목록을 불러오지 못했어요`와 재시도 버튼 표시

#### 오래된 데이터

- 현재 시각 기준 `lastUpdatedAt`이 36시간보다 오래되면 `데이터가 오래되었어요` 배지 표시
- 오전 9시 이전에는 전날 데이터가 표시될 수 있음을 허용한다.

## 7. API 분석 및 계약

### 7.1 현재 코드에서 확인한 요청

```text
GET /exec?type=active&page={page}&pageSize={pageSize}
GET /exec?type=history&historyStatus=REMOVED&page={page}&pageSize={pageSize}
GET /exec?type={type}&page={page}&pageSize={pageSize}&sigungu={구}&keyword={검색어}
```

- `type`: `active` 또는 `history`, 생략 시 `active`
- `historyStatus`: 이력 상태 필터. 앱은 `REMOVED`만 요청
- `page` 기본값: 1
- `pageSize` 기본값: 20, 최댓값: 100
- `sigungu`: 정확히 일치하는 시군구 필터
- `keyword`: 사건번호·주소·건물명·법원·시군구·동 부분 검색
- 정렬: `auctionDate` 오름차순

MVP 앱 요청은 `pageSize=20`을 사용하고, 고정 조건은 서버 결과와 앱 양쪽에서 검증한다.

### 7.6 매각시간 정규화

실제 응답의 `auctionTime`은 아래처럼 단순한 `HH:mm`이 아니라 Google Sheets의 시간 셀이 Date 객체 문자열로 변환된 값이다.

```text
Sat Dec 30 1899 10:00:00 GMT+0827 (한국 표준시)
```

권장 해결책은 Apps Script에서 시간 전용 변환 함수를 사용해 API가 처음부터 `HH:mm` 형식으로 반환하도록 수정하는 것이다.

```javascript
function timeToApiString(value) {
  if (value instanceof Date) {
    return Utilities.formatDate(
      value,
      AUCTION_CONFIG.TIMEZONE,
      'HH:mm'
    );
  }
  const match = String(value || '').match(/(?:^|\s)([01]\d|2[0-3]):([0-5]\d)(?::[0-5]\d)?(?:\s|$)/);
  return match ? match[1] + ':' + match[2] : String(value || '');
}
```

`convertSheetRowToAuctionItem`에서는 다음처럼 사용한다.

```javascript
auctionTime: timeToApiString(raw['매각시간']),
```

서버가 수정되기 전까지 앱은 다음 순서로 방어적으로 처리한다.

1. `HH:mm` 형식이면 그대로 사용한다.
2. 긴 문자열에서 유효한 첫 `HH:mm`을 추출한다.
3. 파싱하지 못하면 시간을 숨기고 날짜만 표시한다.
4. 1899년 날짜와 `GMT+0827` 문자열은 사용자에게 노출하지 않는다.

### 7.7 고정 조건 검증

서버는 페이지 분할 전에 다음 조건을 적용해야 한다.

```text
sido == "서울특별시" 또는 주소가 서울특별시로 확인됨
appraisalPrice >= 1_000_000_000
isInProgress == true
usageName이 "아파트"로 정규화됨
```

용도 값은 원본 표현 차이를 고려해 앞뒤 공백을 제거하고, 서버에서 정한 아파트 동의어만 허용한다. 오피스텔, 다세대, 연립주택, 주상복합 내 상가 등은 임의로 아파트에 포함하지 않는다.

앱도 수신 항목에 같은 조건을 적용하여 잘못된 항목을 노출하지 않는다. 다만 현재 API처럼 조건 적용 전 목록을 페이지로 나눈 뒤 앱에서만 필터링하면 전체 결과와 페이지 수가 부정확해질 수 있으므로, **고정 조건은 반드시 서버의 페이지 계산 전에 적용하는 것을 원칙으로 한다.**

### 7.8 현재 API의 선행 확인 사항

첨부된 `doGet` 코드에는 `sigungu`와 `keyword` 필터만 있으며 서울·10억 이상·진행 중·아파트 조건을 직접 적용하는 로직은 없다. 실제 첫 페이지 응답은 네 조건을 모두 만족하므로 현재 `auction_items` 시트에는 사전 필터링된 데이터가 저장되는 것으로 보인다. 그래도 다음 중 하나가 구현 전에 계약으로 보장되어야 한다.

1. `syncCourtAuction`이 `auction_items` 시트에 고정 조건을 만족하는 행만 저장한다.
2. 또는 `doGet`이 고정 조건을 적용한 뒤 `totalCount`, `totalPages`, `items`를 계산하도록 수정한다.

두 번째 방식을 권장한다. API 계약 자체가 앱의 목적을 보장하므로 시트에 다른 데이터가 추가되어도 안전하다.

사용자가 제공한 실제 JSON 응답으로 API가 정상 동작하는 환경이 있음을 확인했다. 다만 다른 익명 요청 환경에서는 Google 로그인 화면으로 리디렉션될 수 있었으므로 Android 앱에서 동일 URL을 인증 없이 호출할 수 있는지 최종 빌드에서 확인한다.

- 웹 앱 실행 사용자: 소유자
- 액세스 권한: 로그인 없이 호출 가능한 공개 범위
- 배포 후 실제 `/exec?page=1&pageSize=1` 요청의 `Content-Type`이 JSON인지 확인
- 민감한 스프레드시트 정보가 API 필드에 포함되지 않는지 확인

공개 URL에 비밀 키를 앱에 넣는 방식은 APK에서 추출될 수 있으므로 접근 제한 수단으로 간주하지 않는다. 이 API는 읽기 전용이며 개인·민감 정보를 반환하지 않아야 한다.

## 8. 로컬 데이터 및 신규 판정

### 8.1 저장 목적

- 화면 진입 즉시 최근 목록 표시
- 네트워크 실패 시 마지막 목록 제공
- 전날 목록과 비교한 신규 사건 판정

### 8.2 로컬 모델 예시

```kotlin
AuctionItemEntity(
    itemKey: String,
    caseNumber: String,
    auctionItemNumber: String,
    courtName: String,
    usageName: String,
    appraisalPrice: Long,
    minimumPrice: Long,
    minimumPriceRate: Double,
    failedCount: Int,
    auctionDate: String,
    auctionTime: String,
    address: String,
    sigungu: String,
    dong: String,
    buildingName: String,
    note: String,
    isInProgress: Boolean,
    objectCount: Int,
    collectedAt: String,

    lastSeenAt: Long,
    isNew: Boolean,

```

가격은 `Int` 범위를 넘을 수 있으므로 반드시 `Long`을 사용한다.

### 8.3 신규 판정 규칙

- 첫 번째 성공 동기화: 기준 데이터로 저장하고 모든 항목의 `isNew=false`
- 이후 성공 동기화: 기존 DB에 없는 `itemKey`만 `isNew=true`
- 같은 `itemKey`의 가격·기일 등이 바뀌면 기존 항목을 갱신하되 신규로 보지 않는다.
- 신규 배지는 사용자가 화면에서 본 뒤 즉시 없애지 않고 해당 동기화 동안 유지한다.
- API 전체 페이지 동기화가 성공한 경우에만 사라진 항목을 로컬 목록에서 제거한다.
- 일부 페이지만 성공한 경우 기존 항목을 삭제하지 않는다.

## 9. 데이터 동기화 정책

- 화면 진입 시 캐시를 먼저 표시하고 API를 요청한다.
- 사용자가 당겨서 새로고침할 수 있다.
- 같은 화면 세션에서 불필요한 중복 요청을 막는다.
- API가 매일 오전 8~9시에 원본을 갱신하므로 앱 자체의 정기 백그라운드 작업은 MVP에서 사용하지 않는다.
- 네트워크 연결·읽기 제한 시간을 두고 무한 대기하지 않는다.
- 첫 페이지 응답의 `totalPages`만 신뢰하지 않고 페이지 응답의 일관성을 검증한다.
- 중복 `itemKey`는 하나로 합치고 더 최근 `collectedAt` 값을 우선한다.
- 모든 페이지의 성공을 확인한 뒤 하나의 동기화 트랜잭션으로 캐시를 교체한다.

목록을 무한 스크롤로 표시하더라도 신규 판정과 완전한 오프라인 캐시를 위해 저장소 계층은 전체 페이지 동기화를 수행할 수 있다. 데이터량이 커지면 Paging 도입을 검토한다.

## 10. 앱 구조

기존 프로젝트 규칙에 맞춰 다음 패키지를 사용한다.

```text
feature/auction/
├── data/
│   ├── AuctionApi.kt
│   ├── AuctionDatabase.kt 또는 공통 Room 확장
│   └── AuctionRepository.kt
├── domain/
│   └── AuctionModels.kt
└── presentation/
    ├── AuctionScreen.kt
    └── AuctionViewModel.kt
```

- `data`: HTTP 요청, JSON 변환, Room 캐시, 서버·앱 조건 검증
- `domain`: 가격·날짜 포맷과 신규 판정에 필요한 순수 로직
- `presentation`: 목록 상태와 Compose UI
- 홈 화면: 세 번째 기능 카드 추가
- 앱 셸: `AUCTION` 화면과 상단 제목 연결
- 설정의 시작 화면 선택에는 실제 사용 후 필요할 경우 추가

현재 프로젝트에는 HTTP 및 JSON 직렬화 라이브러리가 없으므로 구현 시 Retrofit/OkHttp와 Kotlin Serialization 또는 동등한 조합을 추가한다. Android Manifest에는 인터넷 권한이 필요하다.

## 11. 오류 및 데이터 방어 규칙

- `success=false`: 서버 오류로 처리하고 `message`는 진단 로그에만 제한적으로 남긴다.
- 응답이 HTML: 배포 권한 또는 로그인 리디렉션 오류로 분류한다.
- JSON 구조 오류: 캐시를 보존하고 새 데이터로 덮어쓰지 않는다.
- `itemKey`가 비어 있음: 해당 항목 제외
- 감정가가 0·음수·파싱 불가: 해당 항목 제외
- 날짜 파싱 실패: 목록 하단에 배치하고 `기일 미정` 표시
- 매각시간이 긴 Date 문자열: `HH:mm`만 추출하고 실패하면 시간 숨김
- `isInProgress=false`: 제외
- 고정 조건 불일치: 제외하고 진단 로그에 개수만 기록
- 중복 사건: `itemKey` 기준 병합
- `page > totalPages`: 추가 요청 중단
- 서버가 같은 페이지를 반복 반환: 무한 페이지 요청을 막고 실패 처리

## 12. 접근성 및 표시 원칙

- 가격 정보는 색상만으로 구분하지 않고 `감정가`, `최저가` 라벨을 함께 표시한다.
- `신규`, `유찰 N회`, `D-N` 배지는 스크린 리더가 읽을 수 있는 설명을 제공한다.
- 사건 카드의 터치 영역은 최소 48dp를 확보한다.
- 긴 주소·건물명은 최대 줄 수를 정하고 말줄임 처리하되 사건번호와 가격은 생략하지 않는다.
- 날짜와 가격은 한국어 로케일로 표시한다.

## 13. 보안·법적 유의 사항

- 앱에는 스프레드시트 ID, 편집 권한, Google 계정 인증 정보를 저장하지 않는다.
- API는 읽기 전용 공개 데이터만 반환한다.
- 법원 경매 정보는 변경·취소될 수 있으므로 화면 하단에 다음 안내를 표시한다.

> 이 목록은 간편 확인용입니다. 입찰 전 매각기일과 사건 상태를 법원 경매정보에서 다시 확인하세요.

- API 원본 사이트의 이용 조건과 자동 수집 허용 범위는 운영자가 별도로 준수한다.
- 앱은 투자 판단, 권리분석 또는 입찰 결과를 보장하지 않는다.

- `type=history&historyStatus=REMOVED` 전체 페이지를 진행 중 목록과 분리된 Room 테이블에 캐시
- 종료 사건 카드와 안내 영역에서 낙찰·취하 등 정확한 사유를 확인할 수 없음을 명시
- 진행 중일 때 저장한 관심 사건 키를 별도 유지하여 종료 사건 카드에서도 동일한 관심 북마크 표시
- 하단 메뉴의 부동산 경매 탭과 `더보기` 탭 기반 확장 구조
- 캐시가 있을 때 새로고침 실패 안내와 기존 목록 유지
- 인터넷 권한과 도메인 단위 테스트 추가

후속 확인 사항은 Apps Script의 익명 호출 가능 여부를 실제 Android 기기에서 검증하고, 서버 `auctionTime`을 `HH:mm`으로 정규화하는 것이다.
